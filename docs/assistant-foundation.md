# Assistant foundation

This implementation combines deterministic background monitoring with optional local-model chat, opt-in background reasoning, a narrowly allowlisted action proposal, and a gated task-risk predictor. It is still not the completed autonomous AI assistant.

## Runtime

- `assistant-engine.ts` runs in Electron's main process and remains active while the window is hidden in the tray.
- It uses the existing single background scheduler for periodic checks and a typed event bus for task, productivity, and learning changes.
- `context-manager.ts` is the authoritative retrieval layer. Rules can retrieve all local summaries; chat requests pass a typed selection, and disabled/irrelevant modules are not queried. A failed selected source is reported as degraded without discarding other selected sources.
- `rule-engine.ts` contains explainable deadline and revision rules. It creates daily priority summaries and urgent findings; it does not use a language model.
- `assistant-repository.ts` stores monitoring preference and deduplicated activity locally. The unique event key prevents repeat findings across scheduler ticks and restarts.
- `assistant-conversation-service.ts` stores conversations and user-authored memories, gathers query-relevant enabled module summaries for chat, and calls a configured provider through `local-model-provider.ts`. The current replaceable adapter uses Ollama `/api/chat`. Requests are limited to loopback hosts, redirects are rejected, and calls time out. A model outage is saved with an accurate unavailable/error response; it is not represented as successful AI output.
- Memory is opt-in globally and per entry. Relevant memories are ranked locally against the current request and recent user turns. Conversations are persisted locally and can be exported with memories through a native save dialog or deleted.
- Chat uses Ollama structured JSON responses. Model output is validated in the main process; negated task requests are rejected by a deterministic intent guard, and a model-suggested due date is discarded unless the user supplied a deadline. Only a clearly requested `task.create` proposal is eligible for approval. The task and proposal status are written in one database transaction. Repeated approval is rejected.
- `assistant-intelligence-repository.ts` stores explicit helpful/not-helpful feedback and action proposals. Task creation is the only LLM-originated mutation; there is no arbitrary command, file, payment, or external messaging action.
- Background local-model reasoning is opt-in, triggered by Planner/Learning events and the shared scheduler, limited to one attempt per hour, uses only enabled Planner/Learning sources, constrains evidence IDs in the JSON schema, and creates at most one activity per local day. Stale results are discarded when a relevant source changes during inference. Every attempted run is recorded as no evidence, no action, recommendation, deduped, stale, or failed; the audit is visible in the Assistant page and included in assistant data export. A live event-triggered evidence-backed activity was verified on Ollama; it is cancellable when disabled and cannot mutate a feature record.
- `task-delay-model.ts` trains a small regularized logistic model only from completed tasks with due dates. It requires 200 examples, 40 per class, a 40-item chronological holdout, and at least a 5% Brier improvement against the training base-rate baseline. Insufficient data leaves predictions unknown. Saved models are versioned and user-deletable.
- Notifications respect the existing Wellness global reminder switch and quiet hours. A single urgent notification is selected per cycle; other findings remain in the activity center.

## Deliberate limits

Ollama is configured at `http://127.0.0.1:11434` with `llama3.2:1b` in the development database. On 2026-11-14, health, multi-turn chat, approved task creation, and a real event-triggered evidence-backed recommendation were verified; temporary verification records were removed. `npm run test:ollama` repeats those checks and reports initial latency/model-residency measurements. The packaged app's native notification and hidden-window background experience have not been validated with the real model. The saved personal task-risk model has not been trained on actual task history. Module-wide export/retention, broader action permissions, connectors, voice, and a floating orb remain later milestones. Do not describe this as fully autonomous AI until the actual background/notification/outcome loop is validated while the user is away.

Migrations 011–021 add conversations, explicit memories with expiry, proposals/feedback, the task model registry, low-frequency background reasoning settings, model artifact integrity metadata, per-domain context preferences, and persistent reasoning decision audit records.
